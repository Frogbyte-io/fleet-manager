# ADR 0021: Windows workstations are managed agentless over OpenSSH Server

Status: Proposed

Proposed: 2026-11-06 (tracking issue [#607](https://github.com/Frogbyte-io/fleet-manager/issues/607), epic [#606](https://github.com/Frogbyte-io/fleet-manager/issues/606), milestone M12). Proposed for maintainer review. It applies the Windows guest transport of [ADR 0015](0015-windows-lab-guest-transport.md) and the brokered access of [ADR 0017](0017-agent-ssh-access.md) to developer workstations. It **amends ADR 0017 decision 7** for registered machines: the guest OS of an endpoint is detected and recorded, and the caller's `--os` becomes a check instead of a choice (decision 4). It reverses nothing else in ADR 0015 or ADR 0017.

## Context

Maintainer decision (2026-11-06): Windows workstations are the next platform; macOS is not a priority. Every developer device, Windows included, should get fleet-wide skills and machine knowledge (inventory plus the Registry) and be workable by agents through Fleet.

What already exists:

- **Transport.** `fleet-provider-ssh` has `GuestShell::PowerShell` (`shell.rs`): a fixed bootstrap with no caller data is the command string, and the metadata blob and script ride stdin as base64 lines read with `[Console]::OpenStandardInput()`. A synchronous exec runs under a guest-side watchdog (#455). Put, collect and detached exec have Windows scripts. All of it is live-verified on Windows 11 with in-box OpenSSH 9.5 and Windows PowerShell 5.1 ([lab.md](../operations/lab.md#windows-guests)), as an administrator and as a standard account.
- **Inventory.** `inventory.rs` has a CIM/.NET Windows probe (`probe_script_for(GuestShell::PowerShell)`); its tool set reports `unknown`, and checkout discovery is Linux-only.
- **Machines.** `machines exec|put|collect --os windows` already work (ADR 0017); the caller chooses the OS. The machine terminal (`terminal.rs`) sends no remote command, so Windows OpenSSH starts its `DefaultShell` under its pseudo console; one live check worked, but the shell's exit status read as 0 ([machine-terminal.md](../operations/machine-terminal.md#known-limits)).
- **Gaps.** Onboarding (`onboard.rs`), agentless inventory and endpoint resolution (`exec.rs`) hard-code `GuestOs::Linux`, and an endpoint (`fleet-application` `Endpoint`) records no OS. `release_pin` refuses any family but Linux, so `skills_setup` skips Windows, and every Skills Manager script in `skills.rs` (probe/install, deploy, undeploy, catalog rollout) is Bash.
- **Skills Manager v1.40.0** publishes `skills-manager-cli-Windows-x64.exe` (sha256 `03d8bf92f3bd4a70f9bcad2d908bf1c04d1e72deebf3e800b27e78dabb09e370`, the GitHub release digest; the downloaded file matches). It is a PE32+ x64 console binary with **no Authenticode signature**. There is no Windows arm64 asset. Upstream keeps its library and SQLite database in `~/.skills-manager` (`dirs::home_dir`, so `%USERPROFILE%\.skills-manager` on Windows) and its settings in `dirs::config_dir()\skills-manager` (`%APPDATA%\skills-manager`) ([central_repo.rs](https://github.com/xingkongliang/skills-manager/blob/v1.40.0/src-tauri/src/core/central_repo.rs)). Agent skill directories are home-relative (`.claude/skills`, `.codex/skills`, ...; a `.config/<x>` path also checks `%APPDATA%\<x>`) ([tool_adapters.rs](https://github.com/xingkongliang/skills-manager/blob/v1.40.0/src-tauri/src/core/tool_adapters.rs)). Deploy on Windows tries a directory symlink, then a junction, then a copy ([sync_engine.rs](https://github.com/xingkongliang/skills-manager/blob/v1.40.0/src-tauri/src/core/sync_engine.rs)). Everything is per user: the skills must land in the profile of the account the developer's agents run as.

## Options

### A. Agentless over OpenSSH Server (the Lab transport)

Reuses the provider, host-key trust, brokered access, bounds, audit and the live-verified PowerShell layer. Skill sharing is a controller-initiated SSH session running a fixed script that calls the documented `skills-manager-cli --json` contract, exactly as on agentless Linux. Inventory is a probe on demand or schedule. Costs: the machine must be reachable when a rollout runs (an offline laptop catches up on its next rollout and shows drift until then), observations are point-in-time, and setup needs an elevated step on the workstation.

### B. A Windows `fleetd` service

An outbound connection (ADR 0002/0003) would serve laptops that are rarely reachable and give continuous observations. But a service runs as LocalSystem or a service account, while Skills Manager, its library and the agent directories are per user, so it would still need a per-user component or impersonation to do the one thing this epic needs most. It also brings Windows service hosting, named pipes, update and rollback, and code signing (an unsigned service binary meets the same Smart App Control and Defender questions as the CLI below), which FM-S04 has not resolved. M8 does not need it: [#604](https://github.com/Frogbyte-io/fleet-manager/issues/604) gives `fleetctl` a login and revocable tokens held by the user, which an agent on a workstation uses without any node service.

## Decision

1. **Agentless first (A); a Windows `fleetd` is deferred, not rejected.** Revisit it with a new ADR if offline laptops routinely miss rollouts, continuous observations become a requirement, or reachability without a tailnet is needed. Nothing here closes the door: the endpoint and OS model below is shared with a future node route.
2. **The shell is Windows PowerShell 5.1, set as OpenSSH `DefaultShell`.** It is in-box on every supported version and is what the existing framing, watchdog, put and collect were verified on. `cmd.exe` (the Windows OpenSSH default) is never used, and PowerShell 7 is not required or used as the script shell in this milestone (its native-argument and encoding rules differ; the fixed scripts already parse under `pwsh` in CI, so a later move is cheap). Onboarding detects the login shell and refuses `cmd.exe` and PowerShell 7 with a reason that names the setting, instead of failing later.
3. **Script delivery and quoting are ADR 0015's, unchanged.** The command string is the fixed bootstrap; caller values are data in the blob (`$args`, environment, working directory) and are never interpolated into PowerShell or a command line. New fixed scripts (#608, #609) are 5.1 syntax, read no profile state, and write no `.ps1` file except where detached exec already does. When a fixed script passes a value to a native program (5.1 builds the command line itself and does not escape embedded quotes, ADR 0017 decision 12), the value must match a strict grammar checked in the application and again in the script (skill names `[a-z0-9-]`, agent ids from the fixed set, hex digests); a value containing `"`, ending in `\`, or holding a control character is refused, never escaped. No `.cmd` or `.bat` file is ever run with caller data.
4. **The OS is detected at onboarding and recorded on the SSH endpoint.** `machines onboard test` runs, after the host-key check, one fixed shell-sniffing command with no caller data (for example `echo fleet-shell %OS% $PSVersionTable.PSEdition $PSVersionTable.Platform`, whose output differs under Bash, other POSIX shells, `cmd.exe`, Windows PowerShell and PowerShell 7). Only Windows PowerShell 5.1 classifies as `windows`; POSIX output keeps today's Linux behaviour. The result is shown at review and stored on the endpoint (an endpoint, not the machine, because a Windows PC can also expose a WSL `sshd` that is a Linux endpoint). Inventory, skills, exec, put, collect and terminal read it; a caller's `--os` becomes a check that refuses a mismatch (`guest_os_mismatch`, as Lab does) instead of a choice. Existing endpoints are **unknown**, not `linux`: until onboarding or the next inventory probe (which runs the same sniff first) records their OS, they keep today's behaviour, where the caller's `--os` chooses, so Windows Lab and persistent machines that work now keep working. Once an endpoint's OS is recorded, this amends ADR 0017 decision 7: the caller no longer chooses it.
5. **Supported: Windows 11 x64, Pro, Enterprise or Education, on a feature update Microsoft still services, with the in-box OpenSSH Server.** Home works with the same in-box components but is not tested. Windows 10 22H2 reached end of support on 2025-10-14, extended security updates aside ([lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro)); it is not refused and not tested. Windows Server is a Lab guest, not a workstation target. **arm64:** onboarding, inventory, exec, put, collect and terminal are architecture-neutral and allowed; the Skills Manager install is skipped with the existing `unsupported_architecture` reason until upstream publishes a Windows arm64 asset (x64 emulation is not attempted). Fleet reports the edition, version and architecture as facts and refuses nothing on them.
6. **Setup is a documented, elevated, one-time step on the workstation, then the normal trust flow.** The runbook (#608) gives the commands: install the `OpenSSH.Server~~~~0.0.1.0` capability, set `sshd` to Automatic and start it, keep the `OpenSSH-Server-In-TCP` rule and scope it to the controller (or the tailnet interface), set `DefaultShell` to `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, turn password authentication off, and install the controller's public key. The fingerprint is read on the workstation (`ssh-keygen -lf %ProgramData%\ssh\ssh_host_ed25519_key.pub`) and confirmed through the existing `machines onboard test` flow; a later key change needs a new confirmation as on Linux. Fleet does not run the setup itself (it has no channel yet), and no private key or password is ever on the workstation's command line or in Fleet Git.
7. **The SSH login is the developer's own account,** because the skills, the Skills Manager library and the agent directories live in that profile. A dedicated Fleet account would install skills its agents never see.
   - *Standard user:* the key goes in `%USERPROFILE%\.ssh\authorized_keys` (only the user, SYSTEM and Administrators on its ACL). Sessions are not elevated; everything in this epic works.
   - *Administrator:* the default `sshd_config` reads `%ProgramData%\ssh\administrators_authorized_keys` for the Administrators group instead ([server configuration](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)). A key there logs in as **any** administrator on that machine, and a key-authenticated session gets the full elevated token with no UAC prompt (seen live: High integrity). Holding `machines.exec` on such a machine is full control of it. The runbook says so, recommends a standard account where the developer can work as one, and the inventory reports whether the session is elevated so the console can show it.
8. **Fleet-owned per-user paths.** The managed CLI is `%LOCALAPPDATA%\fleet\bin\skills-manager-cli.exe`, and catalog rollouts stage under `%LOCALAPPDATA%\fleet\skills\<name>` (the Windows counterparts of `~/.local/bin` and `~/.local/share/fleet/skills`). Each Fleet directory is created with a protected ACL (the user, SYSTEM, Administrators) and checked on every use: a real directory, not a reparse point, owned by one of those three, with no other write grant; anything else is refused, as detached exec's `fleet-lab` directory is. The probe resolves the managed copy, then `skills-manager-cli` on `PATH`; Fleet does not change `PATH`. The install downloads with in-box `%SystemRoot%\System32\curl.exe` (bounded, like Linux), stages beside the destination, checks the pinned SHA-256 with `Get-FileHash`, runs `--version` before placing it (so a blocked binary is reported as `binary_unusable`, never left in place), and moves it with no replace. Fleet never reads or writes `%USERPROFILE%\.skills-manager` or `%APPDATA%\skills-manager`; it only calls the CLI.
9. **Paths for put and collect are ADR 0015 decision 5's Windows rules, unchanged:** drive-absolute with either separator; UNC and device prefixes, alternate data streams, reserved names, trailing dots or spaces, `.`/`..` components and over-long paths refused; duplicates compared case-insensitively. There is no containment root: as on Linux (ADR 0017 decision 10), the login's own ACLs are the boundary. Skill staging paths are relative, checked against `..`, absolute and drive-qualified forms, and contained under the Fleet staging directory.
10. **Terminal is unchanged:** `ssh -tt` with no remote command, so the workstation's `DefaultShell` runs under Windows OpenSSH's pseudo console (ConPTY). #610 settles the exit-status gap.

## What is reused and what is new

- **Reused unchanged:** `GuestShell::PowerShell`, the bootstrap and watchdog, `put`, `fetch`, `detached`, the Windows path validator, brokered access and stored keys (ADR 0017), the terminal, host-key trust, authorization, audit and bounds. Linux behaviour stays byte-for-byte what it is.
- **Extended:** the Windows inventory probe (agent tool facts, feature version, session elevation, `DefaultShell` and shell version), the Skills Manager release table (a Windows x64 pin), and `skills_setup` (no longer skips Windows x64).
- **New:** OS detection and the endpoint OS field (storage migration, API, `fleetctl --output json`, console); PowerShell versions of the Skills Manager probe/install, deploy, undeploy and catalog rollout scripts with their fixture tests; the workstation runbook; a Windows `fleetctl` (below).

## Consequences

- One transport, one trust model and one audit trail for Linux machines, Lab guests and workstations. The controller stays in the data path (ADR 0017), and rollouts reach only reachable machines; drift reporting is how an operator sees one that was missed.
- **Agents on the workstation need `fleetctl.exe`** for the Registry and the `fleet` skill. The Windows binary already builds in CI (informational job), but there is no distribution, and the Linux pilot's `--url` wrapper is a shell script. A `.cmd` wrapper that forwards `%*` is a known argument-injection shape ([BatBadBut, CVE-2024-24576](https://blog.rust-lang.org/2024/04/09/cve-2024-24576/)), so `fleetctl` needs a non-shell way to name the controller before Windows agents use it ([#614](https://github.com/Frogbyte-io/fleet-manager/issues/614), with release binaries in [#615](https://github.com/Frogbyte-io/fleet-manager/issues/615)).
- The `fleet` skill's examples are POSIX-quoted; agents on Windows run them from PowerShell or Git Bash, so the skill needs Windows notes.
- M8 tokens on a workstation are the user's, obtained by `fleetctl login` (#604); Fleet does not push a token over SSH. The Windows at-rest store (DPAPI or Credential Manager) is #604's call.

## Risks

- **Unsigned CLI.** [Smart App Control](https://support.microsoft.com/en-us/topic/what-is-smart-app-control-285ea03d-fa88-4d56-882e-6698afdb7003) (available only on clean Windows 11 installs, where it starts in evaluation mode) blocks unsigned apps it has no reputation for, and Defender may quarantine a binary after it is placed. Fleet reports the outcome (`binary_unusable`, or `absent` on the next probe) and does not retry in a loop; it never adds exclusions or turns protection off. A download with `curl.exe` carries no Mark of the Web, so the SmartScreen prompt for downloaded files is not expected over SSH; #611 confirms both on a real machine, with Smart App Control on and off.
- **Execution policy and language mode.** The bootstrap is a command string, not a script file, so execution policy does not apply to it; detached exec's `run.ps1` already passes `-ExecutionPolicy Bypass`, which a Group Policy setting overrides. Constrained Language Mode (from App Control for Business or AppLocker) breaks the bootstrap and is unsupported; onboarding should detect and report it.
- **Profiles.** Windows OpenSSH runs `powershell.exe -c` without `-NoProfile`. A developer's profile that prints or reads stdin corrupts framing. The Windows 11 default policy (`Restricted`) keeps profiles from loading; a developer who set `RemoteSigned` has profiles that load. Onboarding detects profile output and reports it; the cleaner fix is a shell-independent launcher (open question 2).
- **Admin keys** (decision 7) and **EDR noise** (the watchdog is one extra hidden `powershell.exe` per exec).
- **Cloud placeholders.** Collecting a OneDrive Files On-Demand placeholder downloads it; the size cap and deadline still bound the read.

## Open questions for the maintainer

1. **Account guidance.** Is "the developer's own account, standard user recommended, administrator allowed with a warning" right, or should onboarding refuse elevated sessions unless the operator opts in?
2. **`DefaultShell`.** Requiring Windows PowerShell 5.1 as the machine-wide `DefaultShell` changes the login shell for every SSH user on the workstation. The alternative is a short fixed launcher (`powershell.exe -NoProfile -NonInteractive -EncodedCommand <fixed stage>`) that works under `cmd.exe`, 5.1 and PowerShell 7 alike and also removes the profile risk, at the cost of a new bootstrap to verify live (stdin inheritance under each shell, the 8,191-character `cmd.exe` line limit). Ship the requirement now and the launcher later, or the launcher first?
3. **Windows 10 22H2.** Untested and unrefused, as proposed, or refused outright?
4. **Unsigned CLI.** If Smart App Control blocks it on #611's machine, is "turn Smart App Control off or install the CLI by hand" acceptable, or should Fleet ask upstream for signed Windows releases first?
